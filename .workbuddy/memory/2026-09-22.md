## 把冒烟脚本从 server/tmp 迁到 server/tests/smoke 并入库

### 起因
`server/tmp/` 整体被 gitignore，M2–M6 的端到端冒烟脚本一直游离在仓库外，
别人 clone 下来无法复现验收。用户要求「移到 server/tests/smoke/」。

### 入库范围（用户拍板：仅冒烟脚本）
入库：`_common.py`（新增）、`smoke_m2.py` … `smoke_m6.py`、`probe_types.py`、`dbq.py`。
**不入库**：`api.exe`/`worker.exe`/`importer.exe`、`*.log`、`smoke_m5.out`、
`ui/` 下的浏览器流程与截图、`dbhelp/*`、`mathcmp/`、`pdfprobe/` —— 均为一次性产物或二进制。

### 关键发现：脚本里写死了凭据（差点提交进仓库）
1. **6 个脚本全都硬编码了同一个测试账号口令**（13 字符，sha1 9c42ba），
   `smoke_m6.py` 另有 2 处正确 PIN 字面量。
2. **我第一次的凭据扫描是漏报的**（正则写法有问题，只报了 ui_setup.py）。
   换成正则更严谨、且**只打印长度与 sha1 指纹、绝不打印明文**的扫描器
   （`server/tmp/scan_creds.py`）后才扫全 —— 教训：安全扫描不能只跑一次就信。
3. `ui_setup.py` 与 `ui/flow4.json`/`flow4b.json`/`flow6.json` 也含凭据字面量；
   `ui_setup.py` 因触发安全策略无法读取，**本轮未入库**，待脱敏后再说。

### 做法：凭据外置 + 消除 CWD 依赖
- 用一次性脚本 `server/tmp/refactor_smoke.py` 把凭据值**直接从脚本抽到 `server/.env`**
  （`SMOKE_ACCOUNT` / `SMOKE_PASSWORD` / `SMOKE_PIN`），值全程不经过对话输出；
  `.env.example` 补三行占位 + 注释说明各自用途。
- PIN 的提取规则踩了一次坑：要**只认同一行同时有 `/auth/pin` 与 `expect=200` 的调用**，
  否则会把「非法格式 `abc`（422）」当成正确 PIN；故意错的 `0000`（401）同理必须保留字面量。
- 新增 `server/tests/smoke/_common.py`：按 `__file__` 推导 `SERVER_ROOT` / `TMP_DIR` / `ENV_PATH`，
  提供 `env(key, default=None)`。各脚本删掉自己那份 `env()` 定义，改为 `from _common import ...`。
  于是 **任意 CWD 都能跑**（旧写法 `open(".env")`、`dirname(dirname(__file__))` 迁完就指错）。
- `smoke_m4/m5` 的 `subprocess.run(..., cwd=".")` 改成 `cwd=SERVER_ROOT`：
  Go 侧用 `godotenv.Load()`，它是从**当前工作目录**找 `.env` 的，不固定 CWD 换个目录跑就会缺配置。
- `./tmp/worker.exe`、`./tmp/importer.exe` 改成 `os.path.join(TMP_DIR, ...)`。

### 一个真实的诊断盲点（已修）
`smoke_m5.py` 的 `run_bin` 只在 worker **非 0 退出**时打印日志。但 worker 单条渲染失败时
仍以 0 退出（只记 `failed` 计数），于是首次跑 M5 时 16 项失败却**看不到任何原因**。
已改成成功时也打印 worker 收尾摘要（`claimed=… ready=… failed=…`）。

### 迁移后实跑验证（全部从**仓库根目录**执行，专门验证任意 CWD）
| 脚本 | 结果 |
| --- | --- |
| smoke_m2.py | 36 通过 / 0 失败 |
| smoke_m3.py | 72 通过 / 0 失败 |
| smoke_m6.py | 94 通过 / 0 失败（与 9-21 基线一致） |
| smoke_m4.py | 106 通过 / 0 失败（走 worker.exe / importer.exe 新 cwd） |
| smoke_m5.py | **首次 16 项失败 → 复跑 107 通过 / 0 失败** |

M5 首次失败的归因：`print` 渲染器是**懒启动且失败会记住不重试**的，首次 Chromium 冷启动
没起来 → 任务回落 `queued` → 后续断言全挂。手动跑一次 worker 立刻 `claimed=2 ready=2 failed=0`，
复跑 107/107 全绿 —— 属偶发，与路径改造无关（M4 走同一条新 cwd 却全绿，可作旁证）。
